# 복숭아 주문 정리 — 판독팀 오케스트레이션

## 제1원칙

**틀린 값 하나가 빈 칸 열 개보다 나쁘다.** 잘못 배송되면 되돌릴 수 없다.
추측 금지, 보정 금지, 확인 안 한 걸 확인했다고 말하기 금지.
보고는 언제나 **아는 것 / 모르는 것 / 확인 필요한 것**으로 나눈다.

## 팀 구성

| 역할 | 에이전트 | 하는 일 | 권한 |
|---|---|---|---|
| 판독 | `peach-reader` | 이미지에서 보이는 글자만 추출 + 근거 기록 | 읽기 전용 |
| 검증 | `peach-checker` | **스스로 먼저 읽고** reader 결과와 대조 | 읽기 전용 |
| 팀장 | `peach-lead` | 두 보고를 판정, 사용자 보고문 + 기록용 JSON 작성 | 읽기 전용 (쓰기 불가) |
| 실행 | 나(메인) | 에이전트 호출, 중복 검색, 승인 후 시트 기록 | Bash |

팀장에게 실행 권한이 없는 것은 의도된 설계다. **승인 없이 기록되는 경로가 구조적으로 없다.**

## 0단계 — 입력 형태 확인 (건너뛰지 말 것)

| 입력 | 처리 |
|---|---|
| 이미지 **파일 경로** | 전체 파이프라인 (1→4단계) |
| 대화창에 **직접 붙여넣은 이미지** | **`extract_pasted.py` 로 파일을 꺼낸 뒤 전체 파이프라인.** 아래 참조 |
| **카톡 대화 내보내기(.txt)** | **`kakao.py` 로 먼저 묶고** 묶음별로 읽는다. 아래 참조 |
| 순수 텍스트 주문 | 내가 항목을 뽑고 3단계로. 애매하면 추측 말고 질문 |

경로가 실재하는지 Read 로 먼저 확인한다. 없으면 거기서 멈추고 알린다. 진행하는 척하지 않는다.

### 카톡 원문을 받았을 때

주문은 대개 카톡으로 온다. 사용자가 대화 내보내기 파일을 주면 **직접 읽지 말고
먼저 묶는다.** 한 주문이 여러 메시지에 흩어져 있어 그냥 읽으면 놓친다.

```bash
cd peach-bot && python kakao.py <내보낸파일.txt>
```

보낸사람별 묶음이 나온다. 그 다음 내가 묶음마다 판단한다:

- **보낸사람 이름 = 보내는사람 후보.** 손글씨로는 못 읽던 값이 여기선 확실하다.
  단, 고객이 "보내는분:" 을 따로 적었으면 그쪽이 우선이고, 카톡 이름이 별명·상호면
  사용자에게 확인한다. 임의로 확정하지 않는다.
- `📷 사진` 표시가 있으면 **그 묶음엔 캡처가 따로 있다.** 사용자에게 그 사진을 달라고
  요청한다. 사진 없이 그 묶음을 완결된 주문으로 취급하지 않는다.
- `⚠️ 가려진 번호` 는 채우지 않는다 (기존 규칙과 동일).
- `🧮 총 N박스` 는 개별 수량 합과 **검산**하고 결과를 보고한다.
- `(주문 신호 없음)` 묶음도 임의로 버리지 않는다. 잡담으로 보이면 그렇게 보고하고 넘어간다.

한 묶음에 여러 건이 들어있을 수 있다(묶음 = 대화 단위지 주문 단위가 아니다).

**양식대로 온 주문**(`받는분:` / `연락처:` / `주소:` / `수량:`)은 `parse.py` 가 그대로
읽으므로 판독이랄 게 없다. 그래도 3단계(사용자 확인)는 건너뛰지 않는다.


### 붙여넣은 이미지 꺼내기 (2026-07-30 추가)

붙여넣은 이미지는 디스크에 없어서 서브에이전트가 Read 할 수 없다. 하지만 세션
트랜스크립트(`~/.claude/projects/*/<세션ID>.jsonl`)에 base64로 들어있다. 이걸 꺼내면 된다.

```bash
cd peach-bot && .venv/bin/python extract_pasted.py          # 리눅스/맥
cd peach-bot && .venv/Scripts/python.exe extract_pasted.py  # 윈도우
```

절대경로가 한 줄에 하나씩 나온다(`inbox/<날짜시각>/order_01.png` …, **원본 순서 유지**).
그 경로를 그대로 1단계 reader 에 넘긴다. 이러면 붙여넣기도 정식 교차검증을 탄다.

- 기본은 **마지막 붙여넣기 묶음만** 꺼낸다. 이전 대화의 이미지까지 필요하면 `--all`
- 추출 직후 **Read 로 한 장 열어 순서와 내용이 맞는지 눈으로 확인**하고 넘어간다
- `inbox/` 는 고객 이름·전화·주소가 찍힌 이미지라 **gitignore 되어 있다. 커밋하지 말 것**

**추출이 실패했을 때만** 단독 판독으로 내려간다. 그때는 **"교차검증 없이 단독 판독했다"고
반드시 명시**하고 3단계로 간다. 조용히 넘어가지 않는다.

> 2026-07-30, 이 경로가 없어서 12건이 교차검증 없이 기록됐다. 판독 자체는 나중에 대조해
> 보니 이름·전화·주소 모두 맞았지만, **맞았다는 건 결과론이고 그때는 알 수 없었다.**
> 추출을 건너뛰지 말 것.

## 1단계 — 판독 (peach-reader)

절대 경로를 넘긴다. 이미지 여러 장이면 장당 한 번씩.

## 2단계 — 교차검증 (peach-checker)

`같은 절대 경로 + reader의 JSON` 을 넘긴다. checker는 스스로 읽은 뒤 대조한다.
**reader → checker 순서가 의미이므로 병렬 실행하지 않는다.**

reader 나 checker 중 하나라도 실패하면 그 사실을 팀장에게 그대로 전달한다. 숨기지 않는다.

## 3단계 — 팀장 판정 (peach-lead)

`peach-lead` 에 **두 보고서 전문**을 넘긴다 (요약해서 넘기지 않는다 — 요약하다 정보가 사라지면
팀장이 잘못 판정한다). 팀장은 항목별 판정, 사용자 보고문, 기록 가능 행만 담은 JSON을 돌려준다.

**팀장의 보고문은 손대지 않고 그대로 사용자에게 전달한다.** 매끄럽게 다듬는다며
⚠️ 를 지우거나 보류를 통과로 바꾸지 않는다. 덧붙일 말이 있으면 보고문 아래에 따로 적는다.

### 중복 확인 (팀장 JSON을 받은 뒤, 기록 전)

기록 대상의 받는사람마다:

```bash
cd peach-bot && .venv/Scripts/python.exe peach.py search 홍길동
```

겹치는 기존 기록이 나오면 **사용자에게 보여주고 중복인지 물어본다.** 내가 판단하지 않는다.

## 4단계 — 사용자 승인 후 기록

사용자가 **명시적으로 "기록해"** 라고 하기 전에는 쓰지 않는다. 보류 행은 넣지 않는다.
수정 요청이 오면 표를 고쳐 다시 보여주고 다시 승인받는다.
(수정이 판독 자체를 뒤집는 수준이면 1단계부터 다시 돌린다.)

```bash
cd peach-bot && .venv/Scripts/python.exe peach.py add '[{"받는사람":"홍길동","받는분전화번호":"010-1234-5678","수량":"5kg 1박스","주소":"서울시 ...","보내는사람":"김철수","보내는분전화번호":"","비고":""}]'
```

건수가 많거나 따옴표가 꼬이면 스크래치패드에 `orders.json`(UTF-8)으로 쓰고 **경로를 그대로 넘긴다**:

```bash
cd peach-bot && .venv/Scripts/python.exe peach.py add "<orders.json 절대경로>"
```

**파이프(`| peach.py add -`)는 쓰지 말 것.** 윈도우 stdin 이 cp949 로 잡혀 한글 키가 깨지고,
깨진 키는 빈 값으로 조용히 기록된다(2026-07-24 실제 발생). 파일 경로 방식은 UTF-8 로 직접 읽는다.

**날짜 구분 빈 행은 자동이다.** 마지막 기록일과 오늘이 다르면 `add` 가 구분용 빈 행 1줄을
알아서 넣고 그 아래부터 기록한다(2026-07-24 사용자 요청). 같은 날 추가 입력은 이어 붙인다.
내가 따로 빈 행을 만들 필요 없다. 넣지 않으려면 `--no-separator`.
빈 행은 `count`/`recent`/`search` 의 건수에 세지 않으며, `delete-last` 도 건수로 세지 않고
남게 되면 함께 정리한다.

기록 후 반드시 `recent N` 으로 **값이 실제로 들어갔는지 눈으로 확인**한다.
"N건 기록 완료"는 행 개수만 보장하지 내용을 보장하지 않는다.

스크립트 출력(`✅ N건 기록 완료`)을 **그대로** 보고한다. 실패하면 실패를 그대로 보고한다.
성공했다고 임의로 말하지 않는다. 기록 후 보류 행이 남아 있으면 무엇이 남았는지 다시 짚어준다.

## 조회 · 삭제

```bash
cd peach-bot && .venv/Scripts/python.exe peach.py count
```

- `recent [N]` — 최근 N건 (기본 5)
- `search <검색어>` — 받는사람/주소로 검색 (중복 확인)
- `backup` — 지금 시트를 CSV로 저장 / `restore <csv> --commit` — 백업으로 되돌리기

## 삭제 — 실전 데이터다 (2026-07-24부터)

**시트에 들어있는 건 실제 배송될 주문이다. 지우면 주문이 사라진다.**

삭제 계열(`delete-last`, `delete-name`, `clear`, `restore`)은 **기본이 미리보기**다.
`--commit` 없이 실행하면 무엇이 지워지는지 출력만 하고 시트는 그대로다.

내가 지켜야 할 순서:

1. **`--commit` 없이 먼저 실행**해서 지워질 행 목록을 사용자에게 보여준다
2. 사용자가 그 목록을 보고 **"지워"라고 다시 말해야** `--commit` 을 붙인다
3. `--commit` 시 스크립트가 자동으로 CSV 백업을 뜬다. 백업 경로를 사용자에게 알린다

**금지**: 사용자가 "지워"라고 한 번 말했다고 곧바로 `--commit` 붙이기.
미리보기를 보여주는 단계를 생략하지 않는다. 애매하면 지우지 않는다.

`clear` 는 추가로 **현재 건수를 정확히 맞춰** 적어야 실행된다:
`clear --confirm-count <현재건수> --commit`. 건수를 내가 임의로 추정해 넣지 않는다 —
반드시 `count` 로 확인한 실제 숫자를 쓰고, 그 숫자를 사용자에게 보여준 뒤 실행한다.

되돌리기: `restore backups/<파일>.csv --commit` (복원 직전 현재 상태도 자동 백업된다)

## 항목 판독 규칙 (공통)

- 없거나 불확실하면 빈 값. 추측 금지
- 전화번호 축약/마스킹(`010...1234`)이면 빈 값
- 받는사람(고객) ↔ 보내는사람(발송인) 혼동 금지. 확정 못 하면 둘 다 비우고 물어본다
- 이미지 한 장에 여러 건이면 각각 별도 행
- "총 N박스" 같은 합계가 적혀 있으면 **각 행 수량의 합과 맞는지 검산**하고 결과를 보고한다

### 허용되는 정규화 — 아래 4개가 전부 (2026-07-24 사용자 확정)

1. **존칭 제거, 직함 유지**: `귀하/님/씨/앞` 은 뺀다. `본부장/팀장/회장/사장/대표/과장/부장`
   같은 **직함은 이름의 일부로 남긴다**. 헷갈리면 빼지 말고 그대로 두고 물어본다
2. **전화번호 구분자만 `-` 로 통일**: `010_3273_1229` → `010-3273-1229`.
   **숫자는 절대 변경·보완하지 않는다**
3. **"보내는사람도 동일함" 명시 시** 받는사람 값을 보내는사람에 복사. 문구가 없으면 추정 금지
4. **품종·특이사항은 비고에 원문 그대로**: `천중도`, `황도`, `착불` 등. 해석·분류하지 않는다

주소는 정규화 대상이 **아니다.** 띄어쓰기·마침표·`107-1405` 표기 전부 원문 유지.
이 4개 외의 변형을 했다면 사용자에게 **반드시 알린다.**

## 이 파이프라인이 못 하는 것 (사용자에게 감추지 말 것)

- **주소가 실재하는지 검증하지 못한다.** 우편번호·도로명 대조를 하지 않는다. 판독이 일치해도
  원본 자체가 틀렸으면 그대로 들어간다
- **전화번호가 유효한지 확인하지 못한다.** 자릿수만 본다
- reader·checker 가 **같은 방식으로 같이 틀릴** 수 있다. 두 판독 일치가 정답 보증은 아니다
- 붙여넣은 이미지도 추출만 되면 교차검증을 탄다. 단, **추출에 실패하면 단독 판독으로
  내려가고 그건 검증이 아니다** (0단계 참조)

이 한계를 사용자가 물으면 그대로 답한다. 더 확실한 척하지 않는다.
